About

Renux is a modern BSD operating system, designed to be easy to maintain and debug, with a focus on portability and performance. The whole tree is meant to be understandable and modifiable, and it builds from a single portable script on any Unix host.

Features

sched_renux

An ULE-derived scheduler, now the default, tuned for CPU-bound throughput with aggressive balancing and preemptive work stealing.

RENUX_MALLOC

A lock-free kern_malloc fork with deep per-CPU bucket caches, enabled by default in GENERIC.

Aggressive VFS

renux_vfs_cluster and renux_vfs_subr ship aggressive I/O clustering defaults for storage throughput.

Full preemption

FULL_PREEMPTION on by default in GENERIC cuts dispatch latency throughout the kernel.

Renux Build System

One script for everything: ./renux build for world and kernel, plus iso, qemu and release targets.

Portable cross-build

Cross-builds from FreeBSD, Linux, NetBSD, OpenBSD, DragonFly or macOS, without any preinstalled toolchain.

MD/MI separation

Machine-dependent code lives under sys/arch/, keeping the bulk of the kernel machine-independent and ready for new ports.

Hackable by design

One renux for the whole tree, a machine-independent core and a self-contained cross-build on any Unix host make Renux easy to understand, modify and rebuild.

Get Renux

Clone the source tree and build it yourself:

user $ git clone https://github.com/renuxproject/src.git /usr/src/renux
user $ cd /usr/src/renux
root # ./renux build
root # ./renux iso
root # ./renux qemu

Roadmap

  • Done MD/MI separation: machine-dependent code under sys/arch/, the rest of the kernel is machine-independent.
  • In development Installer: a first-class installer to put Renux on disk, driven by bsdinstall on the live image.
  • Planned RSL — Renux Subsystem for Linux: run Flatpak and CLI Linux programs through a bhyve VM (Alpine/Void Linux) shown on the Renux screen. Planned tools: rsl-init, rsl-shell, rsl-install (C99 + Zig build).
  • Planned More architectures: port beyond amd64 — i386, arm64, RISC-V, PowerPC and others are the current target for portability.
  • Planned Linuxulator: run Linux binaries natively in the kernel.
  • Planned Zig-based shell and core utilities.
  • Planned Zig build as an alternative system build orchestrator.

Community-Driven & Decentralized

Renux is a community-driven project, decentralized by principle. There is no central authority, company or platform that owns or controls Renux.

Development and infrastructure may be distributed across different people, communities and organizations, which may keep their own repositories, mirrors, services and versions of the system.

Anyone can get the source, host it anywhere — a self-hosted forge, a mirror or a tarball — and build their own version of Renux. Forks, variants and independent efforts are legitimate parts of the ecosystem, not treated as competition.

There is no single path to Renux. There are independent projects that share the same philosophy.

Decentralization policy ›

How Decentralization Works

  • Governance — no person or entity has absolute authority; important decisions are public and open to discussion.
  • Mirrors & infrastructure — the repository is not a single point of failure; anyone may host a mirror or forge and keep developing.
  • Forks — forks and variants are first-class citizens; none needs permission to be called Renux.
  • Distribution — there is no mandatory official repository; communities keep their own and users choose whom to trust.

Hackability

Being hackable is part of the Renux philosophy: the system is meant to be understood, modified and rebuilt by whoever uses it. What keeps it hackable:

  • One build script — ./renux build rebuilds world and kernel; no preinstalled toolchain required.
  • Machine-independent core — MD code lives under sys/arch/, so hacking a port touches one place.
  • Modular components — kernel, init, libc and userland can evolve relatively independently.
  • Any Unix host — cross-builds from FreeBSD, Linux, NetBSD, OpenBSD, DragonFly or macOS.
  • Your own Renux — community-driven and fork-friendly: hacking the system can become your own line of development.
